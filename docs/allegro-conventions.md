# Allegro conventions the OpenAPI spec does not tell you

Observed by probing the Allegro **sandbox** on **2026-10-15** (`scripts/spike-conventions.mjs`, run by `.github/workflows/spike.yml`; ~50 requests, read-only). These are observations of the sandbox on one day, not guarantees: re-run the spike (see the end) when behaviour looks different, and treat anything marked _unverified_ with care.

## Findings and what the library does about them

| #   | Observation                                                                                                                                                                                                                                                                                       | Consequence                                                                                                                                                                                                       |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **`Accept` must be Allegro's vendor type.** `application/vnd.allegro.public.v1+json` works; `application/json`, `*/*`, `text/html`, `...beta.v1+json` on a public-only endpoint, `...public.v2+json`, `...v1+xml` all give **406**                                                                | The client sets the vendor type by default. Overriding `Accept` with something generic breaks the call; only use the documented beta type per endpoint. The 406 happens before authentication (also on `upload.`) |
| 2   | **`Content-Type` on writes: `application/json` and `text/plain` give 415.** No `Content-Type` at all was accepted (the request got as far as authentication), as was the vendor type                                                                                                              | The `json` option defaults the content type to the vendor type. String bodies are sent without a content type on purpose (like 1.x), never as `text/plain`                                                        |
| 3   | **Error bodies have two families.** API errors: `{ errors: [{ code, message, details, path, userMessage, metadata }] }`. OAuth/security errors: `{ error, error_description }`. The token endpoint without credentials returns both: `{ error: 'Unauthorized', error_description, errors: null }` | The default policy rejects on a truthy `error` or `errors`, so all of them arrive as before. `Errors` now includes `metadata`. 404 for a missing resource has `code: 'ERROR'` and the real class in `details`     |
| 4   | **`trace-id` response header** on every API response (not on token endpoint responses), a 16-hex id                                                                                                                                                                                               | Hooks report it as `requestId`; errors keep it in `err.headers.get('trace-id')`. Quote it when contacting Allegro support                                                                                         |
| 5   | **No rate-limit headers** (nothing like `x-ratelimit-*`, no `retry-after`, no `deprecation`/`sunset`) in 12 sequential requests. No 429 was provoked on purpose                                                                                                                                   | `retry429Policy` stays correct without them (falls back to exponential backoff). Do not build logic on remaining-quota headers                                                                                    |
| 6   | **`www-authenticate: Bearer realm="oauth2-resource", error="...", error_description="..."`** on 401s, same info as the body                                                                                                                                                                       | Nothing needed; the body is enough                                                                                                                                                                                |
| 7   | **401 error codes:** no/invalid scheme: `unauthorized` ("Full authentication is required..."); malformed token: `invalid_token` ("Cannot convert access token to JSON")                                                                                                                           | Both arrive as `{ error, error_description }`. Re-authorization logic should treat `invalid_token` (and `invalid_grant` from the token endpoint) as the signal                                                    |
| 8   | **Token endpoint accepts parameters in a form body and in the query string** (both gave identical answers), and **only HTTP Basic client authentication**: credentials in the body give `invalid_client`                                                                                          | Form body stays the default (no secrets in URLs). `tokenParams: 'query'` is not needed but harmless                                                                                                               |
| 9   | **`client_credentials` works for a device application** and returns an application token: `expires_in` 43198 (~12 h), a long scope list, JWT claims `iss, exp, client_id, jti, scope, allegro_api` (no `iat`, no `user_name`)                                                                     | The planned `client_credentials` flow (Phase 2) is feasible without a user. Expiry from the JWT `exp` fallback works for these tokens                                                                             |
| 10  | **`GET /me` with an application token returns 500**; with no or an invalid token 401                                                                                                                                                                                                              | `/me` is only meaningful with a user token. Do not use it as a generic health probe with application tokens                                                                                                       |
| 11  | **A bogus refresh token gives `invalid_grant` ("Invalid refresh token: ...") whatever `redirect_uri` is** (omitted, empty, or the literal `undefined`)                                                                                                                                            | The 1.x `redirect_uri=undefined` bug could not be shown to matter for invalid tokens; whether it matters for valid ones is _unverified_. The library omits the parameter when unset                               |
| 12  | **`User-Agent` is not enforced**: custom, default, empty and `curl` all got 200                                                                                                                                                                                                                   | Sending an application-identifying User-Agent is good practice, not a requirement (as of this run)                                                                                                                |
| 13  | **Lenient routing:** trailing slash works; unknown query parameters are ignored (200). `HEAD` gives 405, `OPTIONS` 403, `DELETE` on a read-only resource 405 (`NotAllowedException`)                                                                                                              | A misspelled query parameter fails silently: typed query parameters (planned) are worth having. The client has no `head`/`options` helper on purpose                                                              |
| 14  | **Redirects:** `/` answers 308 to `developer.allegro.pl`, `GET` on the token endpoint 302 to the login page                                                                                                                                                                                       | Irrelevant for API calls. `fetch` drops `Authorization` on cross-origin redirects                                                                                                                                 |
| 15  | **Device flow:** the code request needs no user; `expires_in` 3600 s, `interval` 5 s; `verification_uri_complete` is the verification page with `?code=<user_code>`; polling early gives `authorization_pending` ("User has not authorized the device code yet.")                                 | Matches what the README and the live tests assume                                                                                                                                                                 |
| 16  | **Responses are gzip-compressed and chunked**; `content-type` carries `; charset=UTF-8` (the casing of `charset` differs between endpoints)                                                                                                                                                       | `fetch` decompresses transparently. Do not compare content types with `===`; test with `includes`/regex                                                                                                           |

## Not covered (needs a user token or a different environment)

- Write endpoints and any user-scoped read (`/me` etc.): an application token cannot exercise them, so request/response behaviour of `POST /sale/...` beyond content negotiation is unobserved.
- Binary downloads: the spec declares `application/octet-stream`, `application/pdf`, `text/csv` and `x-application/zpl` for a handful of endpoints (e.g. label download answers `application/octet-stream`). Whether those endpoints reject the vendor `Accept` type (as in #1) is _unverified_. When using `raw: true` for them, set `Accept` to the media type the specification lists for that response.
- Rate limiting: no 429 was provoked (deliberately). The real limits and the form of the 429 response are unobserved.
- The **production** environment was not probed; sandbox and production may differ.
- Uploads (`upload.` host): only the 404 on `/` and the 406 on a request without `Accept` were observed.

## What an application token can reach

By the specification, only **12 of 270 operations** accept an application token (`client_credentials`), and all are reference data: `GET /sale/categories` (and `/{categoryId}`, `/parameters`, `/product-parameters`), `/sale/category-events`, `/sale/category-parameters-scheduled-changes`, `/sale/delivery-methods`, `/sale/offer-promotion-packages`, `/order/carriers` (and `/ALLEGRO/points`, `/{carrierId}/tracking`), `/billing/billing-types`. 252 operations need a user token, 6 need none. Offers, products and `/me` are in the user-token group, so an unattended CI job without a user can only exercise the reference-data endpoints. The spike observed `/me` returning 500 with an application token; the project owner reports `/me` working on production (with a user token).

## Sandbox: what is known about testing it

Sources: search results and one Allegro GitHub thread read on 2026-10-15. **`developer.allegro.pl` was not reachable from the analysis environment, so the official sandbox pages were not read.** Anything below that is only a search-result summary is marked as such.

- **What it is.** A test copy of the platform on `allegro.pl.allegrosandbox.pl` with its own application registrations (`apps.developer.allegro.pl.allegrosandbox.pl`) and API host `api.allegro.pl.allegrosandbox.pl`. Accounts are created by the developer; Allegro does not create them. Payments use a simulator. Categories and parameters are synchronised from production roughly quarterly, so they can lag (an Allegro expert in the [community forum](https://spolecznosc.allegro.pl/t5/spotkania-z-ekspertami-allegro/13-09-pytasz-i-wiesz-allegro-api/m-p/423743)).
- **Device flow.** Same paths as production on the sandbox host (`/auth/oauth/device`, `/auth/oauth/token`). The 2019 [allegro-api issue #1240](https://github.com/allegro/allegro-api/issues/1240) ("Sandbox AppDevice auth") shows 401s from an _unactivated_ sandbox account; staff asked the reporter to activate the account ("Aktywacja konta" in the account settings) and the thread ended without a confirmed fix. On 2026-10-15 the requests in this repository's live tests worked with a registered device application (see findings 8, 9 and 15 above).
- **Login.** A search-result summary of the official docs says two-step login is not required in the test environment. A third-party design note claims a fixed code `123456` when two-step login is enabled; no Allegro source was found, so **do not rely on it**.
- **Offers via the API.** A [community post](https://spolecznosc.allegro.pl/t5/pocz%C4%85tkuj%C4%85cy-sprzedawcy/sandbox-kod-b%C5%82%C4%99du-offeraccessdeniedexception/td-p/551760) reports `OfferAccessDeniedException` until the sandbox account was verified as a business (seller) account. Unconfirmed for other accounts.

### Can user flows be tested unattended in CI?

**No supported way was found.** The device flow exists so that a person approves the application. No official test mode or fixed approval code was found. Consequences and decisions:

- CI covers everything that works without a user: device code request, `authorization_pending`, token error paths, application tokens and reference-data endpoints (`test/live.test.ts`, the spike).
- Approving a device and everything after it (a user token, `/me`, offers, products) is a **manual or attended** check. An _attended_ run is feasible: a manually started job prints the verification URL, a person approves it while the job polls (the device code lives 3600 s), and the job probes read-only endpoints with the token held in memory only. Nothing is stored.
- **Not done on purpose:** keeping a refresh token in a CI secret (refresh tokens are single use, so every run would have to write the next one back, which needs a token with permission to write secrets, and one failed run breaks the chain); scripting the browser login (needs a sandbox user's credentials as a secret, is fragile, and whether the login page has bot protection is unknown). Revisit only if attended runs become a real burden, and then try a throwaway sandbox user.

## Re-running the spike

```sh
# CI (needs the two repository secrets): Actions > "Spike conventions" > Run workflow,
# or push a change to scripts/spike-conventions.mjs. The report is printed in the job log between
# SPIKE-REPORT-BEGIN and SPIKE-REPORT-END; every probe is one JSON line above it.
# Locally (needs network access to the sandbox):
ALLEGRO_CLIENT_ID=... ALLEGRO_CLIENT_SECRET=... node scripts/spike-conventions.mjs
```

Add a probe by appending a `probe(group, name, url, init)` call to the script; secrets in bodies and headers are redacted before printing (but GitHub also masks secret-like substrings in logs, which can garble a few header values).
